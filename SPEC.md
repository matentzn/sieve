# sieve — System Specification

Status: as-built, reflecting the repository state on the `main` branch. This
document mirrors what the code does today, not what it aspires to. Where a
capability is partial or a gap exists, it is called out in
[Known limitations](#known-limitations).

## 1. Purpose

**sieve** (Scientific Evidence Evaluation & Verification Environment) is a
prototype curation application for reviewing ontology assertions against their
supporting evidence. A curator is shown an assertion (for example, "asthma
`subClassOf` respiratory system disorder") together with the evidence items that
support or contradict it, rates that evidence, and accepts, rejects, or flags the
assertion as controversial. Accepted decisions are exported as RDF axiom
annotations for integration into ontology workflows.

sieve is the human-review-and-export half of a two-tool system with its sibling
[`../mondo-ai`](../mondo-ai). mondo-ai is the upstream **pipeline** — it extracts
candidate assertions from source ontologies, packages them with typed evidence,
scores them, and enriches them with literature and AI synthesis. sieve is the
downstream **curation UI and RDF exporter** — it takes evidence packets, puts a
knowledge steward in front of them, and turns approved decisions into RDF.
mondo-ai depends on sieve as an editable local package (`sieve = { path =
"../sieve", editable = true }`); the evidence vocabulary (CurationStatus,
EvidenceDirection, the SEPIO framing) is shared across both.

## 2. Technology stack

- **Python** ≥ 3.10 with **Pydantic v2** models (hand-written, not generated)
- **uv** for dependency management, **just** as the command runner
- **LinkML** (`linkml`, `linkml-runtime`) for the schema and runtime validation
- **DuckDB** for local curation state (single-file, embedded)
- **Streamlit** for the review web UI
- **rdflib** + **curies** for RDF generation and CURIE→URI expansion
- **Typer** for the CLI
- **Authlib** + **httpx** for ORCID OAuth
- **pytest** / **mypy** / **ruff** for testing, typing, and linting
- **MkDocs Material** for documentation

## 4. Data model

The LinkML schema in `schema/curation_model.yaml` is the source of truth;
`models.py` holds the matching hand-written Pydantic v2 models used at runtime.
(The two are kept in sync manually — the Pydantic models are **not** generated by
`gen-pydantic`, unlike mondo-ai.)

### Packet structure

```
CurationRecord
├── id
├── assertion: Assertion
│   ├── subject_id / subject_label      (e.g. MONDO:0004979, asthma)
│   ├── predicate / predicate_label     (e.g. rdfs:subClassOf)
│   ├── object_id / object_label        (e.g. MONDO:0005275)
│   └── display_text
├── provenance: AssertionProvenance     attributed_to, generated_at, source_version
├── evidence: [Evidence]                (abstract; see subtypes below)
├── evidence_synthesis: EvidenceSynthesis | None   (score, direction, summary)
├── evidence_score: float               Net Evidence Ratio, computed on ingest
├── status: CurationStatus              UNREVIEWED (default), ACCEPTED, REJECTED, CONTROVERSIAL
├── evidence_steward                    ORCID of the deciding curator
└── confidence                          steward's confidence (0–1)
```

### Evidence hierarchy

`Evidence` is an **abstract** class discriminated by `evidence_type`, with four
concrete subtypes, each carrying a `direction`
(SUPPORTS/CONTRADICTS/UNCERTAIN) and an optional `evidence_strength` (0–1):

| Subtype | `evidence_type` | Key fields |
|---|---|---|
| `ConcordanceEvidence` | CONCORDANCE | source, source_subject_id, mapping_set |
| `LiteratureEvidence` | LITERATURE | publication_id, quoted_text, explanation |
| `ExpertReviewEvidence` | EXPERT_REVIEW | reviewer_orcid, reviewer_name, reviewed_at |
| `ComputationalEvidence` | COMPUTATIONAL | method, confidence_score, parameters |

`EvidenceSynthesis` (a recent addition) aggregates a record's evidence into a
single score, direction, and free-text summary — the natural home for AI-produced
overviews coming from mondo-ai.

### Key enums

`CurationStatus` (UNREVIEWED/ACCEPTED/REJECTED/CONTROVERSIAL), `DecisionType`
(ACCEPT/REJECT/CONTROVERSIAL), `EvidenceType`, `EvidenceDirection`
(SUPPORTS/CONTRADICTS/UNCERTAIN), `SourceType`.

## 5. Ingest

`ingest.py` parses YAML evidence packets into `CurationRecord`s and loads them
into DuckDB. `parse_curation_record(data)` builds the model, `ingest_file(path,
db)` loads one file, `ingest_directory(path, db)` batch-loads a tree. On insert,
the record's Net Evidence Ratio is computed (§7) and the evidence array is
serialized to JSON in the `curation_records` table. YAML is the interchange format
because it is human-editable and version-controllable, matching existing ontology
workflows.

## 6. Review UI

`app.py` is a Streamlit application providing the curation loop:

- a dashboard with curation statistics,
- a filterable, paginated record browser,
- an evidence-review panel where the steward rates individual evidence items, and
- decision controls (Accept / Reject / Controversial) that record the decision,
  set the record's status, and stamp the `evidence_steward`.

Packet URLs use Streamlit query params (`?packet=pkt_000001`). Authentication is
via ORCID (§9), with a development-mode bypass.

## 7. Scoring

sieve summarizes a record's evidence as a **Net Evidence Ratio (NER)**, computed
in `db.calculate_evidence_score`:

```
NER = (S⁺ − S⁻) / (S⁺ + S⁻ + S⁰)          range [-1, +1]
```

where S⁺/S⁻/S⁰ are the summed `evidence_strength` over SUPPORTS / CONTRADICTS /
UNCERTAIN evidence items. −1 is unanimous contradiction, +1 unanimous support.

## 8. Export

Two export paths, both driven from the CLI and the UI:

**YAML** (`export.py`) — round-trips curated records back to YAML, one file per
record via `record_to_yaml`, or bundled through `create_export_tarball` /
`export_records_to_directory`. Decisions are folded back into the exported record.

**RDF** (`rdf_export.py`) — the primary deliverable. `packet_to_rdf` emits, per
accepted assertion, an `owl:Axiom` reification annotated with the evidence:

```turtle
_:axiom a owl:Axiom ;
    owl:annotatedSource   <subject_uri> ;
    owl:annotatedProperty rdfs:subClassOf ;
    owl:annotatedTarget   <object_uri> ;
    SEPIO:0000124         <evidence_packet_uri> ;   # has_evidence
    oboInOwl:source       <evidence_steward_orcid> .
```

CURIEs are expanded to full URIs with a `curies` OBO converter; the evidence
packet is referenced nanopub-style via `SEPIO:0000124`. The annotation set varies
by status: ACCEPTED carries the steward ORCID and accepted evidence sources,
REJECTED and CONTROVERSIAL carry `IAO:0000233` (term-tracker item) and, for the
latter, an `rdfs:comment` controversy note. `export_to_rdf(input, output)` batches
a directory of packets into a single Turtle file.

## 9. Authentication

`auth.py` implements ORCID OAuth 2.0 against both the sandbox and production
endpoints. Curators are authorized from a `curators.yaml` file with role-based
access (admin, curator). A development-mode bypass avoids the OAuth round-trip
during local work. Setup is documented in `docs/ORCID_SETUP.md`. ORCIDs recorded
as `evidence_steward` flow into the RDF export as provenance.

## 10. Storage

A single DuckDB file (`data/curation.duckdb`, `db.py`) with two tables:

- **`curation_records`** — one row per assertion: subject/predicate/object,
  the evidence array as JSON, the computed `evidence_score`, `status`,
  `evidence_steward`, and `confidence`.
- **`curation_decisions`** — one row per curator decision: `record_id`,
  `curator_orcid`, `decision`, `certainty`, `rationale`, `decided_at`.

`CurationDatabase` provides CRUD, status updates, per-record decision history,
paginated/filtered reads for large queues, evidence-rating updates, and aggregate
stats. DuckDB was chosen for zero-setup embedded operation with native JSON.

## 11. CLI

Typer app (`cli.py`), invoked as `sieve <command>`. Four commands:

| Command | Purpose |
|---|---|
| `sieve run` | Launch the Streamlit review UI |
| `sieve ingest -I inbox/` | Load YAML evidence packets into DuckDB |
| `sieve export -O rdf -o out.ttl` | Export curated records to RDF or YAML |
| `sieve validate -I inbox/` | Validate packets against the LinkML schema |

## 12. Validation

`validators.py` validates evidence packets against `schema/curation_model.yaml`
using LinkML's `Validator` with the `JsonschemaValidationPlugin` (open-world).
`validate_json_schema(data, target_class="CurationRecord")` checks one dict,
`validate_packet(path)` a YAML file, and `validate_packets(path)` a directory,
returning LinkML `ValidationReport`s whose `Severity.ERROR`/`FATAL` results mark
failures.

## 13. Testing and tooling

`just test` runs `pytest`, `mypy`, and `format` (ruff). **pytest is green: 77
passed.** `mypy` and `ruff` currently report pre-existing debt across the codebase
(implicit-Optional Typer defaults, missing third-party stubs for `yaml`/`linkml`,
unformatted files) — this predates the current work and is tracked as a follow-up
(§14). Other recipes: `just pytest`, `just doctest`, `just mypy`, `just format`,
`just _serve` (local docs).

The LinkML schema must generate a JSON Schema (`gen-json-schema`) for validation
to work — this is exercised by the `validators.py` test suite.

## 14. Known limitations

- **mypy / ruff not green.** `just test` gates on `mypy` and `ruff`, but both
  carry pre-existing errors (≈46 mypy errors across 10 files, ≈16 ruff lint
  findings, 9 files needing `ruff format`). These exist in unmodified committed
  files (e.g. `auth.py`), so they are baseline debt, not a regression. Bringing the
  static-analysis gate green — adding `types-PyYAML`, an `ignore_missing_imports`
  override for `linkml`, resolving the Typer implicit-`Optional` defaults, and a
  one-time `ruff format` pass — is a dedicated follow-up.
- **Schema/Pydantic drift risk.** `models.py` is hand-written to match
  `curation_model.yaml` rather than generated. The two can drift; mondo-ai avoids
  this by generating its Pydantic models from LinkML via `gen-pydantic`.
- **URL routing.** The UI uses Streamlit query params (`?packet=…`) rather than
  REST-style paths; a FastAPI + templates rewrite is noted as a future option if
  bookmarking/sharing becomes important.
- **Evidence-model consolidation.** sieve's polymorphic evidence hierarchy is one
  of ~15 evidence models across Monarch. A shared, importable evidence microschema
  (a flat SEPIO subset) is designed in
  `specs/2026-07-12-evidence-microschema-design.md` and proposed for the wider
  ecosystem; sieve's subtypes are intended to become extensions of that shared
  core.
